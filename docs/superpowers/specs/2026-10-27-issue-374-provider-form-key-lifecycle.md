# #374 — Scope key clearing to the provider form operation

**Status: OWNER APPROVED 2026-10-28.**
**Risk: High** (credential lifecycle and destination binding). Approved: form-owned clearing and retention only in existing masked fields during unrelated operations, with failed-refresh blocking and no new persistence/API. Implementation and verification remain required; no real-key inspection, owner configuration mutation or deployment is authorized.
Baseline: `11e16d1b8e43141d296b801ee663a351ae3fe415`.

## Root cause and existing authority

The issue's supplied runtime evidence is accepted, not rerun. `uploader/public/settings.html:send` unconditionally clears `providerApiKey` in `finally`, including for Set default, Save AI settings and provider deletion. `reloadSettings`/`applyAi` then re-render provider rows while deliberately retaining the open form. Thus the name/URL survive but the pending replacement key disappears; a later Save can instead offer to move the old stored key to the edited URL.

The approved `2026-10-19-ai-provider-registry-design.md` §§4, 6–7 and `SECURITY.md` **Secrets** remain authoritative: keys belong to a provider, blank preserves its stored key, explicit null removes it, the open form's Test can use its typed key, stored keys never go to an unsaved URL, and a stored-key destination move requires explicit confirmation. Server-side secret-first/settings-second partial failures still require deliberate reconciliation.

## Proposed implementation contract

1. Remove DOM key-field mutation from generic `send`. Keep dropping `body.apiKey` in its `finally` so the request object does not retain that reference after completion. A request for `/settings`, a different provider or an unrelated row action must neither read nor clear the pending form key.
2. Put key-field clearing in the provider form's Save and confirmed Remove stored key handlers. Capture the validated provider identity, kind, URL and typed key into that operation's request body; clear the password input **at request handoff, after validation/confirmation and before awaiting the request**. This preserves the existing clear-on-success/refusal/network/partial-failure behavior and prevents a delayed unrelated request from clearing a subsequently typed key. Cancellation or local validation failure sends nothing and retains the pending key.
3. Use the existing `form` object identity to ensure completion work from an old provider operation cannot close or erase a newly opened provider form. `openForm` already creates a distinct object. Post-response close/error placement belongs only to the originating form; still refresh saved registry state and report the completed operation without echoing its key. Do not introduce a second credential cache or copy the key into registry state.
4. Preserve an unrelated open Add/Edit form across successful `applyAi`/`reloadSettings`, including its masked key input, name, URL, kind and provider identity. Continue re-homing the same form node rather than rebuilding it. Saving after unrelated actions must send the typed replacement only in the original form's provider POST/PUT, never in `/settings` or another provider's request. A typed replacement plus changed URL must not fall into the stored-key-move confirmation path; a genuinely blank key plus changed URL still must.
5. Cover the existing secondary discard path: `reloadSettings` currently closes the form on GET failure. If that refresh followed an **unrelated** action, retain the pending form node/key in memory but mark registry state unavailable (`saved=null`) and disable provider Save/Remove/Test and registry actions until fresh settings are available. Do not reinterpret an edited provider as a new provider because its registry lookup is unavailable. `renderProviders` must not treat unavailable registry data as confirmed provider deletion. Show a localized explicit reload-required error; do not overwrite it with an unrelated success message. A deliberate page reload/navigation can discard the form; there is no browser persistence or new recovery API. A successful settings response proving the edited provider no longer exists may close that obsolete form, with an explicit explanation; never retarget its key to another row.
6. Preserve intentional clearing on Cancel, switching to a different Add/Edit form, switching Add to local LM Studio, confirmed removal, and leaving the page. 401 continues the login redirect; do not stash credentials to survive it. These are explicit form/session boundaries, not incidental consequences of an unrelated save. Form Test continues using only the current form's URL/key; automatic model discovery continues using only each saved provider's own credential and saved URL.

No server endpoint, credential read surface, slot, encryption, storage, assignment policy, inference behavior or provider URL validation changes. No new key in `localStorage`, `sessionStorage`, DraftGuard, DOM attributes, URLs, logs, status text or serialized settings. The existing masked password input and request-local body are the only pending-key holders. JavaScript cannot promise physical memory zeroization; remove references rather than claiming erasure.

Affected implementation: `uploader/public/settings.html`; `uploader/test/admin-actions-dom.test.ts` (existing VM page harness and real settings/provider route harness). New failure/discard explanation copy, if needed, belongs in DE/EN `site/src/i18n/ui.ts` and the existing admin copy projection. Update the SECURITY.md **Settings failure residual** sentence to distinguish clearing a **submitted provider-form key** from preserving an **unsubmitted key during unrelated settings work**. Reconfirm all other Secrets guarantees unchanged. Do not retrofit unrelated legacy Settings strings.

## Verification contract after approval

Use synthetic, unmistakably fake keys only; assertions must not print request bodies or secrets on successful runs. Extend real page-script tests, not a hand-reimplemented `send` helper.

- Add form with name/URL/key → Set default on another row → form remains open with all values unchanged → Save sends that key only to `POST /ai-providers`; clears input and never echoes it. Repeat with Save AI settings and deletion of an unrelated unassigned provider.
- Edit provider A with a different URL and typed replacement → Set default B / Save AI settings → subsequent PUT targets A and includes the replacement. Assert no stored-key-move confirmation, no write to B's key, no typed key in `/settings`, model-discovery requests, output or browser storage. Contrast blank-key URL edit: old/new URL confirmation still required; declining keeps form unchanged.
- Unrelated request rejection/network failure followed by successful settings refresh preserves the form/key. Failed refresh retains a visibly blocked form/key, no provider mutation/Test can run against missing registry state, and no false success replaces its reload-required message. Authentication loss follows login handling without persistence.
- Delay an unrelated settings response while typing/changing the form: its completion must not erase the new input. Delay a provider Save, then switch form: completion cannot clear/close the new form. Submitted request remains bound to the original provider/URL/key snapshot.
- Provider Save clears its submitted key on 2xx, 4xx, `settings_partial_failure`, network unknown outcome and 401; Remove stored key clears on its confirmed request; validation refusal/declined confirmation do not. Retain existing clear-on-cancel/local-kind tests and stored-key refusal for unsaved URLs. Verify failure statuses and no implicit retry.
- Extend `admin-actions-dom.test.ts`'s **settings.html against the real settings and provider routes** harness: use disposable settings and fake secret storage, not production credentials. The real route must store the replacement under A's slot and leave B's slot unchanged; settings responses expose only presence. This closes the gap between a correct captured JSON body and actual slot binding.
- Actual browser acceptance in an isolated app: two fake remote provider entries and controlled local test endpoints; perform Add/Edit with both unrelated actions. Inspect masked field continuity, warning/confirmation transitions, request destinations and synthetic request payloads. Block settings refresh to exercise the unavailable-state UI. Never contact a real provider or use an owner key. Any evidence artifact must omit key values.
- Main implementer runs affected uploader tests/typecheck, site i18n tests/`astro check` if copy changes, and full affected CI. No checks are claimed here.

No native dependency is recorded. Reuse the existing provider registry and its approved authority; #273 identity, #283 language routing and #287 navigation do not require a new credential API. This is not a draft-storage feature or a reopening of the provider-registry storage decision.

Rollback only the Settings client/copy change; no data migration or automatic secret restoration. Already committed settings/secret outcomes require the existing explicit reconciliation, not inference that a UI rollback undid them.
